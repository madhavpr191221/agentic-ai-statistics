# MCP Traffic Analysis

Statistical performance analysis of agentic AI systems.

MCP Traffic Analysis is an experimental systems project that measures how task structure, agent autonomy, orchestration architecture, system load, and transport affect the latency, traffic, cost, and reliability of MCP-based AI agents.

The central question is:

> What does the communication and performance behaviour of an agentic AI system actually look like when measured?

The project begins at the Model Context Protocol (MCP) application layer. MCP provides a concrete boundary where agent decisions become observable requests, tool executions, responses, errors, and causal traces. Later experiments can connect these observations to HTTP, TLS, TCP, and IP behaviour.

## What we will measure

For every agent run, the measurement system will eventually correlate:

- model inference spans;
- MCP methods such as `tools/list` and `tools/call`;
- selected tool names and invocation order;
- serialized request and response sizes;
- protocol, queueing, backend, and end-to-end latency;
- successes, failures, retries, and error classes;
- concurrency, resource utilization, and queue length;
- agent turns, handoffs, and complete execution traces.

An execution will be represented as a causal trace or graph:

$$
T_r = (V_r, E_r),
$$

where the vertices are events such as model calls, MCP interactions, and backend operations, and the edges represent ordering or causal dependence.

Important response variables include:

$$
N_{\text{calls}}, \qquad
D_{\text{trace}}, \qquad
B_{\text{request}}, \qquad
B_{\text{response}}, \qquad
L_{\text{total}}, \qquad
P(\text{failure}).
$$

## Research questions

- How many MCP calls does one user request generate?
- Which tools dominate call volume, byte volume, and elapsed time?
- Are latency, payload size, and run cost distributions heavy-tailed?
- How does total latency divide across model inference, MCP communication, queueing, and backend execution?
- Are failures associated with particular tools, payload sizes, load levels, or invocation sequences?
- How variable are traces generated by repeated semantically equivalent prompts?
- Does increased autonomy produce longer, more expensive, or less reliable traces?
- How do single-agent and multi-agent orchestration differ?
- Where does system performance begin to degrade as offered load increases?

## Experimental strategy

The study progresses from controlled measurement to increasingly realistic agent systems:

1. Validate the recorder with deterministic MCP tools and no language model.
2. Measure synthetic workloads with controlled latency, payload size, concurrency, and injected failures.
3. Add a real agent and correlate model, MCP, and backend spans.
4. Run repeated experimental campaigns for task structure, autonomy, orchestration, load, and transport.
5. Analyze distributions, tails, failure probabilities, trace graphs, and queueing behaviour.
6. Extend measurements from MCP to HTTP, TLS, TCP, and IP.

The networking progression is:

$$
\text{MCP}
\rightarrow
\text{HTTP}
\rightarrow
\text{TLS}
\rightarrow
\text{TCP}
\rightarrow
\text{IP}.
$$

Queueing theory will supply baseline models for relating arrival rate, service time, utilization, queueing delay, and concurrency. The purpose is not to assume that agent workloads obey simple queues. It is to measure where those models work, where they fail, and how agent feedback, retries, bursts, and tool dependencies change the system.

## Technology

- Python 3.13
- [uv](https://docs.astral.sh/uv/) for Python and dependency management
- FastMCP for MCP clients and servers
- FastAPI for the local experiment and analysis API
- React, TypeScript, and Vite for the primary research workbench
- Plotly for interactive empirical distributions and trace views
- OpenAI Agents SDK for the initial agent runtime
- NumPy, pandas, SciPy, and statsmodels for statistical analysis
- PyArrow for analysis-ready experiment tables
- NetworkX for trace-graph analysis
- Matplotlib and seaborn for research figures

Google ADK, notebook tooling, external dashboard infrastructure, databases, and packet capture are deliberately deferred until an experiment requires them. The local scientific UI is part of every completed phase; statistical calculations live in tested Python modules rather than browser-only code.

## Project setup

Install the pinned Python version and create the default development environment:

```powershell
uv --cache-dir .uv-cache python install 3.13
uv --cache-dir .uv-cache sync --locked
npm install
```

Add the statistical analysis dependencies to the environment when needed:

```powershell
uv --cache-dir .uv-cache sync --locked --group analysis
```

Verify the environment:

```powershell
uv --cache-dir .uv-cache run python --version
uv --cache-dir .uv-cache lock --check
uv --cache-dir .uv-cache sync --locked --all-groups --check
```

The project-local cache flag works around a Windows cache-path problem on the original development machine. It is safe to use elsewhere, and `.uv-cache/` is ignored by Git.

## Current status

Phase 3 now adds a real GPT-5.6 Sol IT-incident agent over a deterministic local MCP world. It records model time, ordered MCP calls, exact stdio frame bytes, action safety, objective task success, tokens, and estimated cost. See [`docs/phase3_it_incident_agent.md`](docs/phase3_it_incident_agent.md).

The corrected 30-run result memo is [`docs/results/phase3_incident_pilot_results.md`](docs/results/phase3_incident_pilot_results.md). It also documents the invalid first calibration and why it was rerun rather than silently rescored.

Run `npm run demo`, open `http://127.0.0.1:8000`, and choose **Incident Agent**. Real runs require `OPENAI_API_KEY` in the ignored `.env` file.

The application-layer research protocol, Phase 1A recorder validation, and the Phase 2 controlled statistical baseline are implemented. Phase 2 uses a deterministic MCP tool to measure the effect of transport, payload size, service time, and concurrency; it records actual `stdio` JSON-RPC frame bytes and produces reproducible analysis tables and model diagnostics.

Run the primary React/TypeScript workbench:

```powershell
npm run demo
```

Then open `http://127.0.0.1:8000`. The UI runs experiments, browses persisted traces, compares selected runs, and displays descriptive summaries, ECDFs, reproducible histograms, box plots, timelines, failures, and raw events.

Run one deterministic trial:

```powershell
uv --cache-dir .uv-cache run python -m mcp_traffic_analysis.fixtures.runner echo
```

Available scenarios are `list_tools`, `echo`, `sleep`, `backend_exception`, `tool_error`, `timeout`, `nonexistent_tool`, `concurrent`, and `cancellation`. Each run creates an ignored directory under `artifacts/phase1a/` containing a versioned `manifest.json` and append-only `events.jsonl`.

Phase 1A does not load `.env` and does not call a model. Request arguments, payload bodies, exception messages, credentials, and environment variables are not recorded. Because in-memory transport bypasses wire serialization, byte fields are deliberately null rather than estimated.

For the full Phase 2 baseline campaign, see [`docs/phase2_statistical_baseline.md`](docs/phase2_statistical_baseline.md). It is intentionally not an agent benchmark: the goal is to establish trustworthy measurements and statistical units before adding agent behaviour.
