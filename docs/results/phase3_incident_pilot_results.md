# Phase 3 IT-Incident Agent: Pilot Results

Status date: **2026-08-27**

Valid campaign: **`incident-pilot-v2`**

Model: **`gpt-5.6-sol`**, low reasoning and low verbosity

## Executive result

The corrected pilot completed 30 fresh agent runs and 30 fresh stdio MCP sessions: ten runs for each of three synthetic incident families. All 30 runs reached the objective terminal state, giving

$$
\widehat p_{\mathrm{success}}=\frac{30}{30}=1.00,
$$

with a Wilson 95% interval of approximately $[0.886,1.000]$. This does not prove perfect reliability. With only 30 runs and no failures, substantial uncertainty remains below the observed ceiling.

The most important finding is not the success rate. All ten orders runs first attempted a restart of `identity-service`, which the synthetic world rejected, before correctly escalating to `identity-service-owner`. The success metric therefore captures eventual safe resolution, but not action efficiency. The action ledger exposes behavior that a final-answer-only evaluation would hide.

## Design correction before the valid pilot

The first campaign, `incident-pilot-v1`, is retained as invalid calibration evidence. It exposed a design error: the scorer required escalation to `identity-service-owner`, while the tools only revealed the service name `identity-service`. Nine of ten orders runs were consequently scored as failures despite correct diagnoses and reasonable escalations.

The world was corrected to expose the frozen owner in dependency evidence. A new live smoke then passed all score components and SDK-to-MCP trace reconciliation. No v1 observations were silently rescored or mixed into v2.

| Quantity | Corrected pilot result |
|---|---:|
| Independent runs/sessions | 30 |

| Model calls | 279 |

| Total estimated token cost | $1.0102 |

Every run passed ordered SDK-tool to MCP-tool reconciliation. Thus the tool sequence shown in the UI is not inferred from the final answer; it is supported by both runtime hooks and server observations.

## Latency, calls, bytes, and tokens

Across 30 runs, total latency had median 20.10 seconds, IQR 2.21 seconds, descriptive p90 23.01 seconds, and descriptive p95 24.35 seconds. The median run used nine model calls and eight MCP calls.

The median latency components were:

| Component | Median per run |
|---|---:|
| Model calls | 17,719 ms |
| MCP client-observed tool RTT | 164 ms |
| MCP server handler work nested inside RTT | 10 ms |
| Orchestration residual | 1,998 ms |

The decomposition is

$$
L_{\mathrm{total}}=L_{\mathrm{model}}+L_{\mathrm{MCP\ RTT}}+L_{\mathrm{orchestration}}.
$$

Handler time is reported inside, not added on top of, MCP RTT. The large gap between 164 ms client RTT and 10 ms handler work is locally observed subprocess, serialization, SDK, and scheduling overhead—not Internet RTT.

The median run used 7,148 tokens, sent 1,671 exact stdio request-frame bytes, and received 28,253 exact stdio response-frame bytes. The first model call median was 1,650 ms ($n=30$); later model calls had median 1,618 ms ($n=249$). These are descriptive observations on one machine and one campaign.

## Scenario-level behavior

| Scenario | Successes | Median latency | Median tokens | Unique tool sequences |
|---|---:|---:|---:|---:|
| Checkout failures | 10/10 | 19.19 s | 7,109 | 3 |
| Image-worker degradation | 10/10 | 19.20 s | 7,116 | 1 |
| Orders API outage | 10/10 | 21.09 s | 8,034 | 2 |

Orders runs were longer and used more tokens because every observed trace contained a rejected restart followed by the required escalation. This is a descriptive association created inside the controlled task design; at ten runs per scenario it is not a broad causal claim about production incident agents.

Within semantically identical scenarios, the mean pairwise normalized trace edit distance was 0 for image-worker, 0.0395 for orders, and 0.0639 for checkout. The overall mean within-scenario distance was 0.0345. Trace variability was therefore small but nonzero, even though final task success did not vary.

## What cannot be concluded

- Failure predictors cannot be modeled from v2 because it contains no terminal failures.
- The upper quantiles are descriptive with only ten observations per scenario.
- There is no queueing-theory result: requests were not generated by a controlled arrival process and no shared server queue was loaded.
- There is no TCP/IP packet claim: the exact bytes are local newline-delimited stdio JSON-RPC frames.
- The campaign compares incident scenarios, not autonomy levels or model families.

The next statistically meaningful experiment should vary one controlled behavioral factor—such as whether rejected remedial actions are allowed—while holding model, scenarios, evidence, and scoring fixed. A later queueing phase should separately introduce a controlled arrival process, shared capacity, and observed waiting time.
